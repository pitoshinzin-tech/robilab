# 今日の文字:照準が「ビュっと飛ぶ」件の調べ(2026-10-01)

読むだけの調査。コードは変えていない。社長の `?debug=1` の数字が来たら、下の「見分け方」で当てはめる。

## 1. 今のコードの流れ(要点)

- 入力:`AimGame.tsx` の `onMove`(`document` の `mousemove`、117〜125 行)。ロック中だけ、1 イベントごとに `filterMovement` → `applyMouse` で `view` を直接書き換える。フレームごとにまとめる処理はない。
- 描画:`requestAnimationFrame` の `frame`(185〜323 行)。その瞬間の `view` から `aimPoint` を出し、`stepTrace` と軌跡の点を足す。補間はない。
- `view` を 0 に戻すのは `start()`(333 行)だけ。ゲーム中に位置を作り直す場所はない。カウントダウン中もマウスは視点に効く。
- ロック:`start()` で全画面を要求し(待たない)、同じクリックで `requestPointerLock({ unadjustedMovement: true })`。失敗したら普通のロックに切り替え(346〜360 行)。`unadjusted` は「promise が返って成功した」ときだけ on。
- `pointerlockchange` / `blur` は筆を上げるだけ。`fullscreenchange` は表示の切り替えだけで、入力側には何も知らせない。
- canvas の大きさは毎フレーム `clientWidth × devicePixelRatio` に合わせる(188〜191 行)。投影の焦点距離は幅から決まる(`view.ts` 56 行)。
- フィルター(`input.ts` 50〜76 行):「大きい」= `max(120 カウント, 8 × 直近16回の中央値)` 超。大きいのが 1 回きりなら捨てる。2 回続けば両方通す。直前に大きい動きを通した後(`burst`)は保留しない。
- 診断:`max |delta| 1s` はフィルター前の値。ただし「直前の 1 秒」しか出ないので、飛んだ瞬間に見ないと消える。

参考の換算:VALORANT 感度 0.4 なら 0.028°/カウント。120 カウント ≈ 3.4° ≈ 板の 9 単位(線の判定の幅 `edge` 3.5 の 2.5 倍)。1920px 幅の全画面なら画面上で約 45px。

## 2. ブラウザの既知の動き(確かさの印つき)

- 【既知・広く報告】Windows の Chrome / Edge で、ポインターロック中に `movementX/Y` がまれに 1 回だけ巨大な値になる。three.js の PointerLockControls などで昔から報告され、Chromium にもバグ報告がある(番号は記憶なので要確認)。普通のロック(OS のカーソルを中央に戻す方式)で起きる。
- 【既知】`unadjustedMovement: true` は Chrome / Edge 88 以降の Windows で使える。OS の加速を通らない生の入力になる。使えないときは promise が `NotSupportedError` で失敗する。
- 【推測】生の入力(`unadjustedMovement` on)なら、上の巨大な値はほぼ出ない。逆に off で遊んでいるなら、飛びの第一候補。
- 【既知】Chrome は `mousemove` を画面の描画(rAF)にそろえて、まとめて届ける。まとめたイベントの `movementX/Y` は合計になる。だから 1 フレームが長引くと、次のイベント 1 回に大きな(本物の)動きが乗る。
- 【既知】`pointerrawupdate` はまとめる前の細かいイベント。`mousemove` を使っている今のコードでは、イベントの回数は「ポーリングレート」ではなく「ほぼフレーム数」になる。
- 【推測・利用者の報告が多い】4000 / 8000Hz のマウスは CPU の負担が大きく、ブラウザでもフレームの引っかかりが出やすい。
- 【推測】ロックを取った直後や、全画面に入った・出た直後(画面の大きさや中央の位置が変わる瞬間)の最初のイベントに、大きな値が乗ることがある。
- 【既知】OS の「ポインターの精度を高める」(加速)は、off のとき(普通のロック)の値に効く。速く動かすと移動量が大きく増える。

## 3. 原因の候補(可能性の高い順)

### 候補1:フィルターの下限 120 カウントが高すぎて、中くらいの飛びを素通りさせる
- 仕組み:下限は「カウント」で決めているので、感度によって意味が変わる。上の例では 119 カウントまでの飛び(画面で約 45px、線の幅の数倍)は、どんなに不自然でも捨てない。ゆっくりなぞっている間は中央値が数カウントなので、実際の判定はほぼ 120 だけで決まる。
- 場所:`src/lib/aim/tuning.ts` の `outlierMinCounts: 120`、`input.ts` 52 行の `limit`。
- 数字の見え方:飛んだ 1 秒に `max |delta| 1s` が 30〜119 くらい。`dropped` は増えない。fps は普通。
- いちばん小さい直し:下限を角度で決める。たとえば `minCounts = max(15, 1.0° / degPerCount)`(1° ≈ 板の 2.6 単位)。`filterMovement` に `degPerCount` から作った `opts` を渡すだけ。本物の速い動きは「2 回続けば通す」で残る。

### 候補2:Chromium の巨大な値(普通のロックのとき)
- 仕組み:`unadjustedMovement` が使えず普通のロックになっていると、2 章の既知の飛びが出る。
- 場所:`AimGame.tsx` 346〜360 行(切り替え)、`onMove`。
- 数字の見え方:`unadjustedMovement off`。`max |delta| 1s` が数百以上。`dropped` が増えていれば、フィルターは働いている(それでも飛ぶなら候補3)。
- いちばん小さい直し:まず on になっていない理由を調べる(下の 4 章の記録に「1 回目のロックの失敗理由」を残す)。on になれば、多くはこれで消える見込み(推測)。

### 候補3:巨大な値がフィルターのすき間を抜ける
- 仕組み:(a) 飛びが 2 回続くと「本物の速い動き」として、保留ぶんも合わせて足してしまう。(b) 本物の速い動きの直後(`burst` が true)の飛びは保留されずに通る。(c) 飛びが ＋ と − の組で来たときは打ち消し合うので問題ないが、同じ向きが 2 回だと (a) になる。
- 場所:`input.ts` 57〜62 行(2 回続いたら通す)、69 行(`!f.burst`)。
- 数字の見え方:`max |delta| 1s` が 120 を大きく超えるのに、その瞬間に `dropped` が増えない。速く動かした直後に起きやすいなら (b)。
- いちばん小さい直し:「2 回続いた」と認める条件に、向きと大きさのそろい具合を足す(例:2 回の向きの cos が 0.5 以上、大きさの比が 3 倍以内)。`burst` 中も「直前の動きの 4 倍超」は保留する。

### 候補4:フレームの引っかかりで、本物の動きが 1 回にまとまって見える
- 仕組み:1 フレームが長引くと、その間の動きが次のイベント 1 回にまとまり、画面では一気に動く。しかもフィルターは、それを「1 回きりの大きい動き」とみなして捨てることがある。すると照準が手とずれて、次のフレームで「飛んだ」「戻らない」と感じる。高いポーリングレート(8000Hz)や GC、軌跡の描画が重いと起きやすい。
- 場所:`onMove` と `filterMovement`、描画ループ(軌跡は筆の 1 回ぶんあたり最大 2000 点を毎フレーム投影している。245〜248 行)。
- 数字の見え方:飛んだ 1 秒の `fps` が、ふだん(例 144)より下がる。`max |delta| 1s` は少し大きい程度。`dropped` が 1 増えることがある。
- いちばん小さい直し:原因を確かめるのが先。まずマウスを 1000Hz にして試してもらう。直すなら、イベント間隔(`e.timeStamp` の差)が長いときは中央値を「時間あたり」に直して比べ、長いフレームの後のまとまった動きは捨てない。

### 候補5:ロック直後・全画面の出入りの直後の飛び
- 仕組み:`start()` は全画面の完了を待たずにロックする。ロックの後で画面の大きさが変わると、最初のイベントに大きな値が乗ることがある(推測)。フィルターはロックごとに作り直すので中央値が空で、下限 120 だけで判断する。カウントダウン中に飛ぶと、始まる前から照準がずれている。
- 場所:`AimGame.tsx` 340〜345 行(全画面)、104 行(`fullscreenchange` は入力に知らせない)、135 行(`onLockChange`)。
- 数字の見え方:スタート直後か全画面が切り替わった直後だけ飛ぶ。遊んでいる途中では起きない。
- いちばん小さい直し:`pointerlockchange` / `fullscreenchange` / `resize` の後 150ms ほどは動きを足さない(`onMove` の頭で時刻を見て return)。

### 候補6:OS の加速(off のときだけ)
- 仕組み:普通のロックだと、Windows の「ポインターの精度を高める」が効く。速く振ったときだけ大きく動き、「飛んだ」と感じる。
- 数字の見え方:`unadjustedMovement off`、`dropped` は 0、速く動かしたときだけ `max |delta| 1s` が大きい。
- 直し:候補2 と同じ(on にする)。だめなら、加速を切る案内を出す(すでに注意書きはある)。

### 候補7(低い):canvas の大きさの変化で、板が飛んだように見える
- 仕組み:全画面の出入りや、DPR の違う画面へ移ると、投影の倍率が変わる。照準の点は画面の中央で動かないので、照準そのものは飛ばないが、板が拡大・縮小して見える。
- 数字の見え方:`max |delta|` に変化なし。
- 直し:基本は不要。

## 4. 診断表示に足すとよいもの(1 回の報告で決めるため)

いまの表示は「直前の 1 秒の最大」だけなので、見逃しやすく、フィルターの判断も分からない。次を足すとよい(実装はしていない)。

記録(`?debug=1` のときだけ、メモリの中の輪っか状の配列に直近 30 件):
- 目立つ動きのたびに 1 行:`t`(ロックからの ms)、`dx`, `dy`, `|d|`、そのときの中央値と `limit`、フィルターの判断(`pass` / `hold` / `drop` / `pair-pass` / `burst-pass`)、角度に直した量(°)。「目立つ」= `|d| > max(20, 4 × 中央値)`、または判断が `pass` 以外。
- 同じ行に:直前のイベントからの ms(`e.timeStamp` の差)、直前のフレームの長さ(ms)、ロックからの ms、最後の `fullscreenchange` からの ms。
- フレームの記録:直近 1 秒の「いちばん長いフレーム」と、25ms を超えたフレームの数。
- 最初に 1 回だけ:UA、`devicePixelRatio`、画面と canvas の大きさ、全画面か、`degPerCount`、ロックの道筋(`unadjusted ok` / `1回目失敗: エラー名` / `普通のロック`)。
- 社長が飛んだと感じた瞬間に押すキー(例:`J`)で「ここで飛んだ」の印を記録する。ロック中でもキーは取れる。

見せ方・渡し方:
- 左上の表示に、記録の最後の 5 行と、いちばん長いフレームを足す。
- 終わったとき・中断したとき(ロックが外れた後)に「診断をコピー」ボタンを出し、全部を JSON で `navigator.clipboard.writeText` する(ボタンのクリックなのでコピーできる)。同じ内容を `console.log` にも出す。
- 社長には「飛んだら J を押す → 終わったらコピーして貼る」だけをお願いする。

この記録で、上の候補は次のように分かれる:
- 印の近くに `pass` の 30〜119 カウント → 候補1
- 印の近くに `pair-pass` / `burst-pass` の数百カウント → 候補3
- 印の近くでフレームが長い、イベント間隔が長い → 候補4
- 印が `fullscreenchange` / ロック直後に集まる → 候補5
- ロックの道筋が `unadjusted ok` 以外 → 候補2・6 も疑う

## 5. 対応(2026-10-01)

データなしでも安全な対策(A〜C)と、1 回の報告で原因を決める診断(D)を入れた。ふだんの操作感(線の太さ・採点・手応え)は変えていない。

- A(候補1):飛びを捨てない下限を「カウント」から「角度」に。`minCounts = max(15, 1.0° / 感度)`(VALORANT 0.4 なら約 36 カウント。前は 120)。値は `tuning.ts` の `outlierMinDeg` / `outlierMinCountsFloor`。
- B(候補3):大きい動きが 2 回続いても、向きの cos が 0.5 以上・大きさの比が 3 倍以内のときだけ本物とみなす。そろわなければ 1 回目を捨て、2 回目を保留して次で判断。速い動きの途中でも、直前に通した動きの 4 倍を超える動きは保留(`outlierPairCos` / `outlierPairRatio` / `burstJumpFactor`)。
- C(候補5):ロック・全画面・画面の大きさが変わった後 150ms(`settleMs`)は、マウスの動きを足さない(フィルターにも入れない)。
- D(診断、`?debug=1` のときだけ):目立つ動きを直近 30 件記録(時刻・dx/dy・中央値・limit・判断・イベント間隔・直前のフレームの長さ・最後の変化からの ms)。判断は `passed` / `burst-pass` / `held` / `pair-pass` / `dropped` / `dropped-held` / `settle-skip`。ロックの道筋(unadjustedMovement の on/off と、1 回目の失敗のエラー名)、J キーの「飛んだ印」、fps の平均・最小、UA・devicePixelRatio・画面の大きさ・感度も入る。名前や ID は入らない。

社長に試してもらう手順:

1. `/aim?debug=1` を開いて、ふだんどおり遊ぶ。
2. 照準が飛んだと感じたら、すぐ **J** キーを押す(何回押してもよい)。
3. 終わったら結果画面の「診断をコピー」を押す(Esc で中断したときは、次の「クリックでスタート」の画面の左上に同じボタンが出る)。
4. コピーした内容を、そのまま貼り付けて送る。

見分け方は 3 章の終わり(印の近くの判断・フレームの長さ・変化からの時間・ロックの道筋)で当てはめる。
