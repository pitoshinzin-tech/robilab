## 1. 目的と成功の基準

### 2-2. 代表の選び方(作った人気の順位を使わない決まり)
人気の公式の数字(使用率)はどのゲームも公式に出ていないので使わない。次の順で選ぶ。
1. **公式が初心者向け・おすすめと書いているキャラ**(公式サイト・公式のはじめてガイドの文)。
2. **最初から無料で使えるキャラ**(基本のキャラ。買わなくても試せるので、診断から来た人がすぐ遊べる)。
3. 1・2 で足りないときは、**ロールの中で公式の説明の向きが違うキャラ**(サブロール・能力の種類)を混ぜる。ロール内に違いがないと「意外と合わない」が出せないため。
- 選んだ根拠(1〜3 のどれか)を 1 体ずつデータに残す。叩き台の候補は `content/drafts/roles.md` の「代表キャラ(v0.2)」列。

### 2-3. 1 体のページに載せるもの
1. 見出し:キャラの名前(公式の日本語表記)+英語表記の小さな行、ゲーム名、公式のロール(原文の表記)。
2. 一言:**自分たちの言葉の要約**(80 字まで。公式の文の言い換えで、使い心地の感想や強さの評価は書かない)。
3. 公式の言葉:かぎ括弧の中に**原文の短い引用 1 つ**(40 字まで)+出典リンク+確認日(デバイスと同じ「公式の言葉はかぎ括弧の中の原文だけ」)。
4. **このキャラの傾向**:4 軸を数字でなく言葉で(例「攻め寄り・直感寄り・チーム寄り・どちらでもない」)。その下に**根拠の表**:軸ごとに「ロールから」か「公式の言葉『…』から」。
5. **このキャラが合うタイプ**:16 タイプのうち近い順に 3 つ(`/type/CODE` へのリンク、タイプのドット絵つき)。
6. 同じロールのほかの代表キャラ(リンク)。
7. 主ボタン「診断して、自分に合うか見る」→ `/diagnosis`(主ボタンはこれ 1 つ)。
8. 出典の一覧と確認日、「公式ではない」の表記(4 章)。
- **載せないもの**:強さの評価(Tier)・使用率・勝率・パッチごとの数値・攻略・画像。アフィリエイトの枠も置かない(4 章の理由)。

## 3. データ

### 3-1. 置き場所と流れ(デバイスと同じ手本)
- 調査の原本:`docs/content/chars/{overwatch,valorant,apex,sf6,dbd}.json` と各 `*-notes.md`(調べた人のメモ・見つからなかったもの)。
- 生成:`scripts/char-data.ts` が JSON を検査して `src/data/chars.ts` を作る(`scripts/gear-data.ts` と同じ形)。画面はこの TS だけを読む。メモは画面に出さない。
- 型(案):

```ts
type CharTagId = "front" | "hold" | "mobile" | "setup" | "ally" | "lone" | "aggro" | "calm";
type CharEvidence = { tag: CharTagId; quote: string; url: string };   // quote は原文 40 字まで
type Char = {
  id: string;            // URL に使う。英小文字・数字・ハイフン(例 "jett", "soldier-76")
  game: GameId;          // games.ts の id
  roleId: string;        // games.ts のそのゲームの role.id に必ずある
  nameJa: string;        // 公式の日本語表記
  nameEn: string;
  officialRole: string;  // 公式の原文の表記(OW のサブロール、Apex のクラスなど)
  summary: string;       // 自分たちの言葉、80 字まで
  quote: { text: string; url: string };  // 1 つ。40 字まで
  evidence: CharEvidence[];              // 0〜2 件。軸が重ならない
  pickedBy: "official-beginner" | "free" | "variety";  // 2-2 の選んだ根拠
  sourceUrl: string;     // そのキャラの公式ページ
  checkedAt: string;     // YYYY-MM-DD

```

### 3-2. 4 軸の傾向の決め方(作った数字にならないための決まり)
キャラの「向いている 4 軸の値」は、**人の感覚で 1 体ずつ数字を付けない**。次の機械的な規則だけで決める。

1. **土台はロールの値**(`games.ts` の `role.target`)。公式のロールにキャラを割り当てるのは一次情報(OW・VALORANT・Apex は公式のロール/クラス)。
2. **公式の言葉にある性格の札(タグ)で少しずらす**。札は 8 種類だけ。1 枚で 1 つの軸を **0.3** だけ動かし、1 体 2 枚まで(同じ軸に 2 枚は不可)。結果は −1〜+1 に収める。

| 札 | 軸と向き | 付けてよい公式の言葉の例(原文にこの意味の語があるときだけ) |
|---|---|---|
| front 前に出る | 攻め +0.3 | 突入・切り込む・前線・仕掛ける・engage・entry |
| hold 守る | 攻め −0.3 | 守る・防衛・陣地・待ち構える・lockdown・anchor |
| mobile 機動 | 直感 +0.3 | 素早い・機動力・すばやく移動・奇襲・flank |
| setup 準備 | 直感 −0.3(戦略へ) | 設置・罠・情報を集める・計画・偵察・recon |
| ally 味方を助ける | チーム +0.3 | 回復・蘇生・強化・味方を守る・heal・revive |
| lone 単独 | チーム −0.3(ソロへ) | 単独・1 対 1・裏取り・ひとりで・lurk |
| aggro 押し続ける | 熱血 +0.3 | 攻め続ける・ラッシュ・猛攻・relentless |
| calm 冷静に狙う | 熱血 −0.3(冷静へ) | 遠距離から精密に・狙い澄ます・じっくり・precision |

3. 札は**原文の引用(40 字まで)と URL がそろったときだけ**付ける。引用はそのまま 1 体のページの根拠の表に出す(だれでも出典で確かめられる)。
4. OW の**公式のサブロール**は、それ自体を札の根拠にしてよい(例:ダメージのフランカー → mobile・lone、サポートのメディック → ally)。サブロールと札の対応は表にしてデータに置き、CEO が確認する。

- **CEO が決めるべき所**:(a)札の 8 種類と、付けてよい言葉の例の表 (b)ずらす幅 0.3 (c)OW のサブロール → 札の対応表 (d)スト6・DbD の割り当て(3-3)。おすすめ案は上のとおり。
- **0.3 の理由**:ロールの値は −1〜+1 の目盛りで、ロール同士の差はたいてい 0.5 以上ある。0.3×2 枚なら、キャラはロールの近くに残り(ロールの説明と矛盾しない)、それでもロールの中で順位に差が出る。
- **違ったら**:幅を 0.2 にすると「意外と合わない」が出る組み合わせが減る。0.5 にするとキャラが別のロールの値に近づき、「公式はタンクなのにサポートの人に合う」のような説明しにくい結果が出る。札を増やすと調べる量と確認が増える。
- **ロールの値そのもの**(`games.ts`)は v0.1 の叩き台(本人の確認待ちの【仮】)のまま使う。ここは作り直さない。キャラの数字はロールの値を土台にしているので、ロールの値を直せばキャラも自動で直る。
- **画面には数字を出さない**:4 軸は「寄り(値が +0.25 以上/−0.25 以下)」「どちらでもない」の言葉だけ。相性も % を出さず、順番と理由の文だけ。数字の細かさが「測った値」に見えるのを避けるため(owner-intent「作った数字を出さない」)。
  - **違ったら(% を出すなら)**:結果ページのロールの % と並ぶので見た目はそろうが、キャラの % は規則で作った値だと注記が要る。おすすめしない。

### 3-3. 公式のロールがないゲームの割り当て
- **スト6**:公式のロールはない。今のスタイル(ラッシュなど)はサイト独自の分類。**キャラをスタイルに入れるときは、公式のキャラ紹介(公式サイトのキャラページ・公式の紹介の文)にそのスタイルを示す言葉があること**を条件にする(例:投げ → グラップラー、飛び道具・待ち → 待ち/差し返し)。見つからないキャラは `matchable: false`(図鑑には載せるが、相性には入れない。ページに「公式の紹介にスタイルを示す言葉がないため、相性には入れていません」)。マウスの「公式の大きさがないため比べられません」と同じ扱い。
- **DbD**:キラーは公式の能力の説明(公式サイト・公式のパッチノート)から型(チェイス・ステルス・設置)を決める。サバイバーは見た目と固有パーク以外の差が小さいので、**固有パークの公式の説明が型を示すときだけ**入れる。足りなければサバイバーの代表を減らし、その型はロールだけの表示にする。
- どちらも、サイト独自の分類であることを 1 体のページとゲームの一覧に書く(「スタイルはロビラボの分け方です」)。
- **違ったら(スト6・DbD を最初は外すなら)**:調査は軽くなるが、D8 の 5 本のうち 2 本で「合うキャラ」が出ず、結果ページの行がそろわない。おすすめは「根拠のあるキャラだけ入れる」。

### 3-4. 出典と確認日
- 使ってよい出典:**ゲーム会社の公式サイト・公式のヘルプ・公式のパッチノート/ニュース・公式の X / YouTube**。ファンの wiki・まとめ・攻略サイト・ニュースサイト(`roles.md` の参考の多くはこれ)は**出典にしない**(調べる手がかりには使ってよい)。
- 1 体ごとに `sourceUrl` と `checkedAt`。ページの下にまとめて出す。確認日から 90 日たったら見直しの対象(運用メモに書く)。
- 公式の日本語表記がないキャラ(新キャラなど)は英語表記で載せ、notes に残す。表記ゆれは公式の日本語ページを正とする。

## 4. 権利

- **画像**:キャラの画像・ロゴ・公式のアート・アイコン・スクリーンショットは**一切使わない**(D6)。ゲームのロゴを真似た文字組みもしない。
- **キャラのドット絵は作らない**(決定)。**理由**:実在のキャラを自前で描いても二次創作で、権利者のファンコンテンツの決まりに左右される。社長が過去に「トレーサー風」をやめた判断(AutoReel Studio、2026-10-02)とも合わせる。代わりに、**ロールの記号**(盾・照準・十字・目・旗などの自前のドット絵、`PixelArt` の形)と、合うタイプのドット絵(16 タイプの既存の絵)で見た目を作る。**違ったら**:絵の素材が社長の作業として 66 体分増え、公開前に各社の決まりの確認が要る。
- **名前と商標**:ゲーム名・キャラ名は文字で、説明のために使う(どのゲームのどのキャラかを示すため)。各ページの下に「〇〇は△△社の商標です。ロビラボは非公式のファンサイトで、各社とは関係ありません」と書く(今のフッターの一文に加えて、ページの中にもゲームごとに)。
- **ファンコンテンツの決まり**:Riot(VALORANT)・Blizzard(OW)・EA(Apex)・Capcom(スト6)・Behaviour(DbD)の公開しているファンコンテンツ/二次利用の決まりを調査で集め、**決まりが求める表記の文を そのページにそのまま入れる**(例:Riot は決まった断り書きを求めている)。
- **アフィリエイトの枠をキャラのページに置かない**(決定)。**理由**:ファンコンテンツの決まりは「キャラを使ってお金を取る」ことに厳しいものが多い。キャラのページは無料の情報だけにして、収益の入口は今までどおりタイプの結果ページとデバイスの画面に置く(キャラのページからは `/mouse` へのふつうのリンクだけ)。**違ったら**:各社の決まりを確かめたうえで枠を足せる。足すなら PR 表記・`rel="sponsored noopener"`。
- 引用は 1 体 1 つ(+根拠の札の短い引用 2 つまで)で、自分たちの文が主になる形にする(引用の要件:主従・出典・かぎ括弧)。

## 5. 「合うキャラ/意外と合わないキャラ」の計算

### 5-1. 今の仕組みを広げる
今の `roleScore(user, target)`(4 軸の距離 d から `round(100 × (1 − d/4))`)をそのまま使い、`target` をキャラの値に変えるだけ。新しいファイル `src/lib/char-match.ts`(`role-match.ts` は変えない)。

```ts
charTarget(char): Axes   // role.target + 札の分(1 枚 ±0.3)、−1〜+1 に収める
rankChars(user, game): { char, score }[]   // matchable のキャラだけ。score の大きい順、同点はデータの順
pickForGame(user, game): { fits: Char[3]; surprise: Char | null }
```

- **合うキャラ**:そのゲームの `matchable` なキャラを近い順に 3 体(ロールをまたいでよい)。
- **意外と合わないかも**:次の条件を**満たすときだけ** 1 体出す(しきい値の数字を作らない決まり)。
  - そのゲームで一番合うロール(今の `rankGames` の best)に入っているキャラのうち、
  - **ほかのロールの一番合うキャラより低い**もの。そのうち一番低い 1 体。
  - =「ロールは合っているのに、ほかのロールのキャラのほうが近い」キャラ。だから「意外」と言える。
  - 当てはまらなければ出さない(その行は合うキャラだけ)。
- 計算はすべてサーバー(結果ページ・1 体のページとも静的/サーバーの描画)。ブラウザに JS を足さない。
- 1 体のページの「合うタイプ 3 つ」は、16 タイプの既定の軸(`parseAxesParam(undefined, code)`、各軸 ±0.6)とキャラの値で `roleScore` を出し、近い順に 3 つ。同点はタイプの並び順。

### 5-2. 「意外と合わない」の見せ方(否定的にしない)
- 見出しは「意外と合わない」を使わず、**「ロールは同じでも、手ざわりが違うかも」**。
- 文の型:「◯◯(ロール名)が合うあなたでも、△△は〈札の言葉:単独で動く〉キャラ。合わないのではなく、遊び方が違うだけ。〈あなたの軸の言葉:チーム〉より〈ソロ〉寄りの日に試すと発見があるかも。」
- 「苦手」「向いていない」「弱い」は使わない。キャラの強さの話にしない(キャラ側の評価に見えないように、理由は**あなたの軸とキャラの札の向きの違い**だけで書く)。
- 理由の文は `mouse-reason.ts` と同じく、決まった規則と言い回しの表(`CHAR_REASON_TEXT`)から作る。言い回しは CEO・社長が直せる 1 か所にまとめる。
- **違ったら(D9 の言葉「意外と合わない」をそのまま見出しにするなら)**:シェアでは目を引くが、好きなキャラを否定されたと感じる人が出る。おすすめは上の柔らかい見出し+小さく「意外な 1 体」。

## 6. 画面

### 6-1. URL(`/c/[slug]` の名刺と衝突しない)
| URL | 中身 |
|---|---|
| `/games` | 5 本のゲームの入口(ゲーム名・ロールの数・代表キャラの数・更新日)。図鑑の目次 |

- `[game]` は `games.ts` の id(`overwatch` `valorant` `apex` `sf6` `dbd`)、`[char]` は `Char.id`。どちらも `generateStaticParams` で全部作り、`dynamicParams = false`(知らない値は 404)。
- `/c/` は 1 文字の名刺専用のまま。キャラは `/games/` の下だけに置くので衝突しない。
- **違ったら(`/chars/[game]/[char]` など短い URL にするなら)**:動きは同じ。将来ゲームごとのページ(ロールの説明・パッチの話)を足すときに `/games/[game]` の下にまとまっているほうが整理しやすいので、こちらをおすすめ。

### 6-2. 一覧 `/games/[game]/chars`
- 上:h1「VALORANT のキャラ図鑑」、1 行の説明(「代表キャラ 12 体。公式のロールと公式の言葉から、どんなタイプに合うかをまとめました」)、`SubNav`(5 本のゲームの切り替え)。

### 6-3. 1 体のページ
- 2-3 の 1〜8 の順。PC は結果ページと同じ 12 列(左 5 列にロールの記号と合うタイプ、右 7 列に本文)、スマホは 1 列。

### 6-4. 結果ページ `/type/[code]` からの導線

  - 条件を満たすときだけ「手ざわりが違うかも:X」(リンク)

### 6-5. ナビ

### 6-6. SEO(静的に作る)
- 全ページ build で HTML(SSG)。`searchParams` を読まない(読むと静的でなくなる)。
- `generateMetadata`:1 体のページは title「ジェット(VALORANT)はどんなタイプに合う?」、description は一言の要約+「合うタイプ:◯◯・◯◯・◯◯」。一覧は「VALORANT のキャラ図鑑|合うキャラが分かる」。`alternates.canonical` を付ける。

## 7. 調査の手順(リサーチ担当が公式から集める)

CEO がゲームごとにリサーチ担当を 5 人並行で振る想定(時間がかかってもよい)。

1. **ゲームの公式の一覧を確かめる**:公式サイトのキャラ一覧ページの URL、公式のロール/クラス/サブロールの名前(原文)、今の全キャラ数、最新のシーズンでのロールの見直しの有無(Apex のクラスの見直し・OW のサブロールなど `roles.md` の【要確認】を全部片付ける)。
2. **代表を選ぶ**:2-2 の順で、ロールごとに 2-1 の体数+予備 1 体。選んだ根拠(`pickedBy`)と、その根拠の公式の文の URL。
3. **1 体ずつ集める**:公式の日本語表記・英語表記・公式のロール・公式ページの URL・**原文の引用 1 つ(40 字まで)**・札の候補と、その札の根拠の原文(40 字まで)と URL・確認日。札は 3-2 の表の言葉があるときだけ。迷ったら札を付けずに notes に書く。
4. **スト6・DbD**:3-3 の条件を満たす根拠があるか。なければ `matchable: false` と notes。
5. **ファンコンテンツの決まり**:5 社の決まりのページの URL、求められる断り書きの原文、禁止事項(お金を取る・広告・画像の扱い)を `docs/content/chars/policies-notes.md` に。
6. **出さないもの**:wiki・まとめ・攻略サイトを出典にしない。使用率・Tier・勝率は集めない。画像は保存しない。
7. **件数の目安**:66 体+予備 約 20 体、出典 URL はおよそ 100〜150 本。
8. **確かめ**:別の担当(レビュー)が、全部の引用を出典で開き直して原文と一字ずつ合うか、札が 3-2 の表に沿っているかを確かめる。合わないものは札を外す(数字を作らない側に倒す)。
9. **CEO の確認**:OW のサブロール → 札の対応表、スト6・DbD の割り当て、`matchable: false` の一覧。

## 8. テスト・重さ・採点・監査

### テスト(Vitest)
- データ:id が重ならない・URL に使える文字だけ、`game` と `roleId` が `games.ts` にある、`sourceUrl`・引用の URL が https、`checkedAt` が日付、`summary` 80 字以内・引用 40 字以内、札は 8 種類のどれかで 2 枚まで・軸が重ならない、`matchable` のキャラは札の根拠かロールの公式の根拠がある、ロールごとの体数が 2-1 の表どおり。
- 計算:`charTarget` が −1〜+1 に収まる、札なしならロールの値と同じ、`rankChars` の順と同点の扱い、`matchable: false` は入らない、「手ざわりが違うかも」が条件を満たすときだけ出る(出る例・出ない例の両方)、理由の文に「苦手」「向いていない」「弱い」が入らない。
- ページ:`generateStaticParams` の数(5 ゲーム・66 体)、知らないゲーム・キャラは 404、全ページに非公式の表記がある、`/type/[code]` の各ゲームの行にキャラのリンクがある。

### JS の上限
- 図鑑のページも結果ページの追加も**サーバーの部品だけ**。増えは 1 ページ 4KB 以内、目標は 0。`docs/design/js-budget.md` に前後の数字を書く(Task 1 と同じ測り方)。
- ブラウザへ送るのは表示に要る分だけ(キャラのデータを client の部品に渡さない)。

### 採点
- `/games`・`/games/[game]/chars`(1 ゲーム)・1 体のページ(2 体)・`/type/[code]`(変えた所)を、追補 8 章の手順で 375/1440 の写真 → 4 観点。合格は 4 観点すべて 8 以上・平均 8.2 以上、`/type/[code]` は 8.5 以上を保つ。3 回で届かなければ CEO に相談。
- Lighthouse(スマホ)の目安:LCP 2.5 秒以下(LCP は h1)、CLS 0.05 以下、SEO 95 以上。

### セキュリティ監査の観点(差分、public-web-security-gate)
- 入力は URL の `[game]` `[char]` だけ。`dynamicParams = false` で知らない値が描画まで行かない。
- 引用・要約は文字として描く(`dangerouslySetInnerHTML` を使わない)。JSON-LD だけは `<` の置き換えを確かめる。
- 外への出典リンクは `rel="noopener noreferrer"`、`target` を付けるなら同じ。公式サイトの URL は生成のスクリプトで https とホストの許可の一覧(各社の公式のドメイン)を検査する。
- CSP は変えない(外の画像・スクリプトを読まない)。`sitemap.ts`・`robots.ts` が出す URL に `/c/`(名刺)や個人の情報を入れない。
- 新しい DB・API・cookie はなし。
